# Closing — read before the read-back: the three lists and the question round

## Close with the review

A definition is a choice between readings the data cannot decide.
Go through the steps before asking: settle it by measurement first,
and if the answer must keep holding, declare a test (`DECLARE TEST`) so a
check decides it again on every import instead of anyone asking
again. Only what no measurement can decide goes to the user — **a
choice between readings, never a statistic**. A question the data
could have answered costs the user's attention twice: once now, and
again when they learn to skim your questions.

The close carries three lists, kept apart:

1. **Definitional choices** — every assumption in a metric definition
   whose basis is your judgment rather than a measurement or a review
   decision. The basis is the marker, never the number. One per
   definition, with its alternative named.
2. **Data findings** — a reconciliation gap, a column whose name lies
   about its content. Facts to explain, not choices to make.
3. **Wishes for more source material** — what resolves neither by
   choice nor by SQL, only by more information from outside: an
   opening position, a prior-year extract, the policy document naming
   the convention. Name each as a specific ask and say which numbers
   shift when it arrives. The ask is a document, not a decision — keep
   it out of the questions.

Before the lists, read back what you served: every defined metric's
headline from `metric_series`, set against a figure already trusted —
a tie-out total, the source's own statement. Validating inputs never
covers this; a defect in the served shape shows in this read in one
line and nowhere else.

Nothing leaves the session as prose that a query can hold: promote
every reconciliation you ran by hand — a tie-out, a cross-check
between two paths — to a permanent validation (`references/validate.md`)
or name it as debt in the read-back. A tie verified in prose is right
today and silently wrong after the next import; a permanent check
runs again whenever the data version moves and says so. The same rule
covers the bases your assumptions claim: a named route ("ties to GL
4* net") is either a disclosed alternative or a check, or the basis
says judgment.

The read-back covers the whole agreed set of metrics, not just what
was defined: name every metric that has no definition yet and what
would close it. Size the review honestly. Name the load-bearing
judgments (entity, additivity, unit, anything a wrong value silently
corrupts) one by one. For a hundred `meaning` annotations exhaustive
review is theater: show the distribution and a spot-check sample, and
treat a failed spot-check as the batch's problem, not the row's.
